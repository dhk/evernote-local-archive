# Session Summary — Local-First Evernote Archive

This document summarizes the design decisions, constraints, and execution plan discussed in this session. It is intended as a durable reference for future work and community discussion.

---

## Context and Constraints

- Current Evernote account exceeds upcoming plan limits.
- Downgrade date: **February 4**.
- Post-downgrade constraints:
  - ≤ 1,000 notes
  - ≤ 20 notebooks
- Current state:
  - ~2,500 notes
  - ~50 notebooks

Primary goal:
> Reduce Evernote footprint by the deadline **without losing access, searchability, or ownership of historical notes**.

Secondary goal:
> Design a solution that could be useful to others, while being built first and foremost for personal use.

---

## Core Design Philosophy

### Guiding Principles

- **Local-first**: All authoritative data lives on the filesystem.
- **Privacy-preserving**: No servers, no accounts, no telemetry.
- **Open source by intent**: Free, inspectable, reversible.
- **Vendor-resilient**: No dependency on Evernote’s long-term viability.
- **Boring technology**: Files, folders, standard formats.

This is explicitly **not**:
- A SaaS
- A new note-taking app
- A sync engine
- A product with a roadmap

---

## High-Level Architecture

### Two-Tier Model

1. **Cold Storage (Source of Truth)**
   - Notes exported as ENEX
   - Stored locally (optionally synced via iCloud Drive)
   - Deterministic folder structure
   - Re-importable into Evernote at any time

2. **Index / Recall Layer**
   - Evernote retained as a search and preview interface
   - Uses *roll-up meta notes* rather than one note per archive item
   - Optional local index (DuckDB) for safety and tracking

Key idea:
> Evernote remains the *memory interface*.
> The filesystem becomes the *archive of record*.

---

## ENEX as the Canonical Format

- ENEX is Evernote’s documented export format.
- It is:
  - Lossless
  - Human-inspectable
  - Reversible
  - Widely supported

Important constraint:
- Evernote does **not** provide a single API endpoint to export everything as ENEX.
- The Cloud API can fetch note data, but bulk export requires custom logic.
- For deadline-driven needs, **desktop export is the most reliable path**.

---

## Evernote Integration Strategy

### Roll-Up Meta Notes

To stay within Evernote limits:

- Avoid one Evernote note per archived item.
- Create **one roll-up note per (notebook, year)**.

Each roll-up note contains:
- Titles of archived notes
- Last-updated dates
- Short summaries (optional initially)
- Local file links to ENEX files
- Basic restore instructions

This approach:
- Preserves discoverability
- Keeps Evernote note count low
- Avoids duplication of content

---

## macOS Integration

### Spotlight Search

- Archive stored locally (e.g., iCloud Drive).
- Spotlight indexes:
  - Filenames
  - Optional plaintext summary files
- User flow:
  1. Search via Spotlight
  2. Select result
  3. ENEX opens in Evernote desktop

This requires no custom indexers or background services.

### Cross-Device Access

- iCloud Drive used for syncing across Macs.
- Spotlight indexing occurs locally on each device.
- Evernote desktop is only needed when restoring full notes.
- Evernote Web can be used for:
  - Roll-up notes
  - Reading summaries
  - Recall on iPhone/iPad

Direct opening of ENEX files in Evernote Web is **not possible** due to platform limitations.

## Optional DuckDB Usage

DuckDB is **optional but recommended**.

It is used as a:
- Local ledger
- Safety rail
- Source of truth for what has been archived

DuckDB tracks:
- Which notes are archived
- Archive paths
- Archive dates
- Deletion safety checks
- Optional summaries and keywords

Key distinction:
> DuckDB is not for search UX — Spotlight and Evernote already do that.
> DuckDB exists to prevent mistakes over time.

The DuckDB–pandas interface is a supported and appropriate way to work with this data.

## Open-Source Posture

- Project is motivated by **enlightened self-interest**.
- Built to solve a personal problem first.
- Shared openly to validate assumptions and invite critique.
- No expectation of contributors, PRs, or long-term maintenance.
- Clear non-goals:
  - No servers
  - No monetization
  - No accounts
  - No background services

Community engagement is framed as:
> “I’m sharing a design early to see what I’m missing.”

## February 4 Execution Strategy (Pragmatic)

### Phase 1 — Deadline-Driven (Now → Feb 4)

Focus: **Get compliant safely and quickly.**

- Choose a simple cutoff rule (e.g., notes last updated before Jan 1, 2023).
- Export old notes to ENEX using the Evernote desktop app.
- Archive entire notebooks where possible.
- Delete archived notes and notebooks from Evernote.
- Create minimal roll-up notes (one per archived notebook).
- Verify counts:
  - Notes ≤ 1,000
  - Notebooks ≤ 20

No automation required.
Elegance is explicitly deferred.

### Phase 2 — Post-Deadline (After Feb 4)

Optional refinements:
- Split batch ENEX into per-note files
- Add DuckDB as a ledger
- Generate summaries
- Improve roll-ups (by year)
- Add Spotlight-optimized companion files
- Incorporate community feedback

---

## Key Takeaways

- This design prioritizes **safety and reversibility** over automation.
- Filesystem-first + ENEX ensures long-term ownership.
- Evernote is used tactically, not as the source of truth.
- DuckDB adds discipline but is not required to meet the deadline.
- The approach is intentionally modest and incremental.
